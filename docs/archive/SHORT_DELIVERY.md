### 一、先完善一个真实可用的产品闭环

- **雪场选择**：结合出发地、出行日期、天数、人数、单双板、水平、预算及偏好；只追问影响推荐的缺项。不以低价或名气直接排序，给出推荐理由、主要取舍和不适合的情况。
- **具体雪场详情**：雪道分级/地图、缆车、开放与夜场、雪票、租具、教学、交通接驳、住宿餐饮、预约与退改规则。逐项附来源、适用雪季/日期、可信度和缺失/冲突说明，不强行补满。
- **行程卡**：日程、交通、预算明细、装备清单、避坑提醒、图片、教学链接与来源形成连贯出口。模板日程与有证据的具体安排分开；不把模板说成已核验的定制路线。
- **总账而不是最低价**：逐步补齐交通、雪票、租具、住宿、按需求的教学及其他必要支出；区分按人/按单、按小时/天/套餐、押金与实际消费、包含与不包含项目。解释错峰、住宿位置、转场和可滑时间的取舍；超预算时提供合理替代方案，不靠漏算费用。
- **费用计算升级**：有足够结构化依据后再按人数、天数和实际需求计算，处理套餐包含项避免重复收费。已知报价、估算、待确认分别展示；缺少必要费用不称完整总预算，报价适用期与信息保鲜期分开。
- **异常与展示验收**：正常出卡、缺价格、缺来源、媒体空态、取消/断开和引用校验失败均验证。真实模型与浏览器验收补齐后，才称完整端到端通过。

### 二、图片与教学视频做扎实

- **图片**：每个目的地先找 4–6 张候选（全景封面、官方雪道图、代表性雪道/初学区、关键设施、住宿/小镇、可选特色场景）。逐张保留出处、作者/机构、日期、所属雪场和授权；候选数量不是强制凑数。
- **展示边界**：宣传图与实拍证据分开展示，过往图片不推断实时雪况。自摄或获得授权素材优先；授权不明不下载分发，原页链接也不冒充已授权本地图片。需要对象存储时再完善现有媒体访问路径，不为了图片先搭复杂平台。
- **视频**：先收集 8–12 条候选，按单板/双板与入门/进阶组织，共用资源池而不是每场找一套。主题包括装备与安全、基础移动/站姿、控速刹停、基础转弯等。
- **内容策展**：核验链接、作者/资质线索、实际内容、适用阶段；观看后才写要点及关键时间戳。推荐原平台跳转，不搬运视频；视频不能替代必要的现场教学。未核验资源保持待确认或空态。

### 四、国际目的地的数据模型与行程支持

- **目的地层级**：区域、成员雪场、住宿落脚点、联票关系分开建模。二世古联合、白马谷、三峡谷不能当作单一雪场混用数据；圣安东与 Ski Arlberg 也需区分层级。
- **名称与别名**：中文、原文、简称和成员名称明确映射；白马谷先做重点成员，不宣称已覆盖全部成员。
- **多币种**：价格显式记录币种、适用日期和计价单位；未换算分别展示。换算保留原币金额、汇率来源和日期，不用现有人民币字段装外币数字。
- **国际总费用**：机票、入境/签证相关费用、地面交通、住宿、雪票、租具等按出发城市、日期、人数、天数和同等服务范围比较。入境、交通和雪票有效范围单独查证，不作实时保证。
- **实施顺序**：先定字段和兼容方案，再通过受控数据库迁移、同步与回归落地；不要求立即换关系数据库或向量库。

### 五、数据库迁移管理与部署收尾

- **现有 MySQL 安全接管**：完整备份并在隔离库验证恢复 → 核对四组漂移与历史 NULL 情况 → 审查默认值、回填及约束调整方案 → 在恢复副本执行并验证数据 → 负责人核对冻结基线后才 stamp。详见 [DATABASE_MIGRATIONS.md](DATABASE_MIGRATIONS.md)。
- **真实 MySQL 验收**：补新空 MySQL 的实际升级、恢复副本的接管和业务读写测试；临时 SQLite 与离线 MySQL SQL 不能替代真实数据库验收。
- **后续改表**：人工审查 Alembic autogenerate，显式处理重命名与数据回填；测试空库升级和旧版本升级，核对失败后的实际结构，不假定 MySQL DDL 能整体回滚。
- **启动生命周期**：有余量再将自动 create_all 与正式部署流程分离，改成显式迁移先行及健康检查；保留清楚的开发初始化流程，不让启动顺手变更生产表。
- **恢复与部署**：备份覆盖业务库、YAML/配置版本、Chroma、会话与获授权媒体等不同资产；验证恢复，部署前检查白名单、调试开关、密钥管理。按实际需要完善已有部署配置，不把“工具接入”写成“生产可用”。

### 六、向量库先管理风险，出现需求再迁移

- **当前继续用 Chroma**：YAML 是真相源、索引可重建；常规 upsert，删减内容或改分块需全量重建，避免遗留旧 ID。补内容校验，不能只比较 ID 数量。
- **重建可靠性**：进一步校验嵌入维度/数值、备份和恢复流程；如需要无中断更新，再设计新集合构建、验证后切换及保留旧集合回退，而不是先删再赌写入成功。
- **迁移触发条件**：避开危险删除仍反复损坏、频繁增删无法接受重建、多进程部署产生实际问题，或实测延迟/资源影响用户体验。12→20 个目的地本身不是触发条件。
- **后端选择**：优先比较 Qdrant 与 pgvector。Qdrant 可保留 MySQL但多一个服务；pgvector 属于 PostgreSQL，保留 MySQL再加 PostgreSQL会增加运维成本。ES/OpenSearch 等到全文检索规模和运维条件确有需要再评估；MySQL 换 PostgreSQL不是本轮前置要求。
- **真正迁移的工作**：抽取存储接口，适配当前 Chroma 私有集合调用、入库/查询、metadata 过滤、BM25 语料与引用元数据；重新标定距离阈值，不能照搬 0.85；跑检索、拒答、分层及跨场隔离回归，并验证回退。

粗略工作量仅供排期：安全/恢复流程核验半天至 1 天；Alembic 基线接入通常 1–2 天（已有部分已完成，旧库漂移另算）；向量新后端基本接通 1–2 天，包含评估、阈值、部署与回退的迁移通常 3–5 天，环境问题预留约一周；同时更换关系数据库可能额外数天至一两周。不是完成时限承诺，不能因时间充裕自动启动所有改造。

### 七、技术增强保留，但让位于真实问题

- 重排与更有分辨率的评测集、引用忠实度指标，按 ROADMAP 推进；新增测试必须能识别实际退化，不以堆题数充当质量提升。
- 数据增长后再考虑 BM25 索引优化；有实际合作和隔离需求再做多租户；有成本/延迟分析需求再完善可观测。
- 图谱先做可溯源可视化，点节点看来源；图数据库与多跳查询按需求触发，不上 GraphRAG。
- 多节点职责拆分和模型路由只在可测收益下推进，不做多个 Agent 平等对话式堆叠；引用体系保持统一。
- 来源与授权逐条登记；平台评价仍暂缓，直到存在合法、可核验的来源路径。

### 八、讨论过但已放弃/明确不做

- 不转向“个人滑行数据沉淀的运动进步 Agent”，不扩跑步/骑行/登山，不做硬件或自动动作评分。早先目标—记录—反馈闭环只是被放弃方向，不作为实施待办。
- 不采用“近郊低价雪场占主体”的配额，不保证最低价，不用高价或名场证明值得；核心始终是少花冤枉钱。
- 不为了显得像 Agent 增加 Agent 数量，不为了技术栈好看而迁库，不以全国数百雪场覆盖作为近期目标，不牺牲可溯源换完整答案。

## 本窗口不要做的操作

- 不在现有 MySQL 直接运行初始 upgrade、stamp、降级或删表重建来消除漂移；先备份并验证恢复副本，单独审查修复方案。
- 当前索引可读，无须为了本轮演示重建。若确需删减资料/改分块，先保存 YAML/配置版本，在停服务后备份完整 Chroma 目录；全量重建只能不指定雪场。重建仍非原子操作，删除后写入失败需恢复备份或重新完整入库。
- 不把价格保鲜期当作报价适用期，不把缺失费用当作零，不宣称实时雪况或最低价。
